# The shader tools

A Wallpaper Engine scene is drawn with its items' own shaders, which are written in a GLSL dialect. At import, Livepaper translates each one to Metal with two command-line tools that ship inside the app and run as separate processes: glslang turns GLSL into SPIR-V, and SPIRV-Cross turns SPIR-V into Metal Shading Language. Drawing never involves them: the extension compiles the MSL that import wrote.

`build.sh` builds both tools from source. Nothing here is downloaded as a binary.

## What is in the build

- `glslang`, glslang's standalone front end, version 16.6.0. The importer uses it to preprocess (`-E`, with `#include` resolved against `-I` directories) and to compile GLSL to SPIR-V (`-V --target-env vulkan1.1`). It is built without HLSL input and without the SPIR-V optimiser (SPIRV-Tools), because the importer feeds it GLSL only and does not ask for optimised SPIR-V. It carries its own SPIR-V header, so it needs no SPIRV-Headers.
- `spirv-cross`, SPIRV-Cross's command line, from the tag `vulkan-sdk-1.4.357.0`. The importer uses its MSL back end (`--msl --msl-version 20400 --msl-decoration-binding`). The command line does not build without its other back ends, so they are in too.
- Both are for macOS arm64 and link only the system's C++ library and `libSystem`. `glslang` is about 3 MB and `spirv-cross` about 4 MB.

The source lists and the flags are at the top of `build.sh`. They are the lists glslang's and SPIRV-Cross's `CMakeLists.txt` files give, compiled file by file with the system's clang. The script writes the three headers those builds generate (glslang's `build_info.h` and `glsl_intrinsic_header.h`, SPIRV-Cross's `gitversion.h`) itself, so it needs neither CMake nor Python. On 189 of the test shaders in SPIRV-Cross's archive, the result gave the same SPIR-V and MSL, byte for byte, as Homebrew's builds of the same versions.

## Licences

Livepaper is MIT. Both tools are under permissive licences, and neither has a condition, like the LGPL's, that decides how it is shipped:

- glslang is mostly BSD-3-Clause. Some of its files are BSD-2-Clause, Apache-2.0 or Khronos's MIT-style licence, and its preprocessor carries NVIDIA's licence. Its parser, `glslang_tab.cpp`, was generated by Bison and is GPL 3 with the Bison exception, which allows it in a larger work under any terms.
- SPIRV-Cross's own files are Apache-2.0 or MIT, and we take Apache-2.0. The SPIR-V headers it compiles in are under MIT and Khronos's free-use licence.

What they ask is that the notices go with the binaries. The texts are in `licenses/`, each name starting with the project it comes from. `glslang-LICENSE.txt` holds every licence glslang uses; the other `glslang-` files are the ones that apply to the files compiled here, one by one. `build.sh` stops if any of them differs from the text in the release's archive. `NOTICE` at the top of the repository names both tools.

## Why a separate process

The reason is isolation, not the licence. The shaders come from Workshop items, which are untrusted input, and glslang and SPIRV-Cross are large C++ parsers. Run as a helper process with a time limit, a crash or a hang in one of them ends that process, never the app. No C++ goes into the Swift package, and the wallpaper extension never runs either tool.

## Rebuilding

```
make shader-tools
```

This needs an Apple silicon Mac with Xcode, and nothing else. The script uses only the system toolchain, so Homebrew cannot leak into the binaries. It downloads both tags' archives from GitHub into `src/`, refuses to go on if a sha256 is not the pinned one, builds, and writes `out/`:

| File | What |
|---|---|
| `glslang`, `spirv-cross` | The binaries |
| `glslang-<version>.tar.gz`, `SPIRV-Cross-<version>.tar.gz` | The exact source archives they were built from |
| `BUILD-INFO.txt` | Versions, sha256s, compiler, flags, source lists, and what the binaries report about themselves |
| `build.sh`, `licenses/` | The script and the licence texts |

`build.sh` checks the result before it installs it. It fails if either binary is not arm64 only, if it links anything outside `/usr/lib` and `/System/Library`, or if it does not report the pinned version (`glslang --version`, `spirv-cross --revision`). Then it makes the importer's calls on a small vertex and fragment pair that includes a header: preprocess, compile to SPIR-V, translate to MSL, and look for `main0` and the texture's binding in the result.

`src/` and `out/` are ignored by git. A second run with the same versions and flags checks the binaries again and stops. A full build takes about 15 seconds on a recent Mac, downloads included.

## Moving to new versions

Change `GLSLANG_VERSION` and `GLSLANG_SHA256`, or `SPIRV_CROSS_VERSION` and `SPIRV_CROSS_SHA256`, in `build.sh`. Check each new sha256 against a second source first, since GitHub's tag archives are not signed: the hash Homebrew's formula pins for the same URL will do. Then compare the source lists in `build.sh` with the release's `CMakeLists.txt` files (glslang's in `glslang/`, `SPIRV/` and `StandAlone/`; SPIRV-Cross's at the top). A file added upstream shows up as an undefined symbol when linking.

If the release changed a licence text, the script stops and says so; copy the new text into `licenses/`, read what changed, and commit it. If the files compiled now carry a licence that is not in `licenses/` (glslang's `REUSE.toml` and SPIRV-Cross's `.reuse/dep5` say which), add it to the lists at the top of `build.sh`.

A release archive has no git history, so `spirv-cross --revision` prints the tag and the commit time the archive's files carry, where a CMake build would print `git describe` and the time it ran. The build is the same every time.

## Where CI publishes it

The `shader-tools` job in `.github/workflows/ci.yml` runs `make shader-tools` on every pull request and every push to `master`, and uploads the whole of `out/` as the artefact `shader-tools-arm64`: binaries, source archives, `BUILD-INFO.txt`, `build.sh` and licence texts together. The `check` job downloads that artefact and runs the tests against it, with `LIVEPAPER_REQUIRE_SHADER_TOOLS=1` so that missing tools fail the tests.

The app's build copies both binaries next to its executable, where `Bundle.main.url(forAuxiliaryExecutable:)` finds them, and signs each on its own ("Bundle the shader tools" in `project.yml`). Each release carries their source archives, build script and licence texts through the same artefact.
